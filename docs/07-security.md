# FixFlow — خطة الأمان وحماية البيانات

## 1. هدف هذا الملف

يحدد هذا الملف متطلبات الأمان والخصوصية في نظام FixFlow.

يستخدم هذا الملف عند:

- تصميم قاعدة البيانات.
- كتابة سياسات RLS.
- إنشاء صفحات تسجيل الدخول.
- تطوير Edge Functions.
- حماية المرفقات.
- إنشاء روابط QR.
- نشر المشروع.
- اختبار النظام.
- التعامل مع الحوادث الأمنية.
- حماية بيانات الشركات والعملاء.

الهدف الأساسي هو التأكد من أن:

- كل شركة ترى بياناتها فقط.
- كل مستخدم ينفذ العمليات المسموحة له فقط.
- الأسرار لا تظهر في الواجهة أو GitHub.
- الملفات والمرفقات لا تكون عامة.
- روابط QR لا تكون قابلة للتخمين بسهولة.
- العمليات الحساسة تسجل.
- الأخطاء لا تكشف معلومات تقنية حساسة.
- البيانات يمكن استعادتها عند حدوث مشكلة.

# 2. أهداف الأمان

يجب أن يحقق FixFlow الأهداف التالية:

## السرية Confidentiality

منع الأشخاص غير المصرح لهم من مشاهدة البيانات.

أمثلة:

- شركة ألف لا ترى طلبات شركة باء.
- الفني لا يرى طلبات فني آخر.
- المبلّغ لا يرى الملاحظات الداخلية.
- المستخدم العام لا يرى بيانات الإدارة.
- الملفات الخاصة لا تفتح دون صلاحية.

## سلامة البيانات Integrity

منع تعديل البيانات بصورة غير صحيحة أو غير مصرح بها.

أمثلة:

- الفني لا يغير دوره إلى مدير.
- المستخدم لا يغير organization_id.
- لا يستطيع الفني إغلاق الطلب دون اعتماد.
- لا يستطيع المستخدم تعديل سجل التاريخ.
- لا يستطيع المبلّغ تغيير حالة الطلب مباشرة.

## التوافر Availability

الحفاظ على عمل النظام والقدرة على استعادة البيانات.

أمثلة:

- وجود نسخ احتياطية.
- مراقبة الأخطاء.
- التعامل مع فشل البريد.
- منع الطلبات المزعجة.
- وجود خطة استعادة.

## التتبع Accountability

معرفة من نفذ العملية ومتى.

أمثلة:

- من غيّر الأولوية؟
- من عيّن الفني؟
- من أغلق الطلب؟
- من عطّل المستخدم؟
- من صدّر البيانات؟

# 5. البيانات التي يمنع تخزينها دون حاجة

لا يجب جمع أو حفظ:

- كلمات مرور المستخدمين داخل جداول النظام.
- أرقام بطاقات الدفع.
- رموز CVV.
- مفاتيح API داخل قاعدة بيانات مكشوفة.
- رقم الهوية الوطنية دون حاجة نظامية.
- معلومات صحية.
- بيانات مالية غير مرتبطة بالخدمة.
- صور شخصية غير لازمة.
- معلومات خاصة لا تساعد على معالجة طلب الصيانة.

تدير Supabase Auth كلمات المرور، ولا يكتب النظام كلمات المرور داخل جدول profiles.

# 6. نموذج التهديدات

يجب التفكير في المهاجمين المحتملين:

## مستخدم خارجي مجهول

قد يحاول:

- تخمين روابط QR.
- إرسال طلبات كثيرة.
- رفع ملفات ضارة.
- تخمين روابط المتابعة.
- إدخال JavaScript داخل الوصف.
- تعطيل الخدمة بطلبات متكررة.

## مستخدم مسجل بصلاحية محدودة

قد يحاول:

- رفع دوره.
- الوصول إلى بيانات شركة أخرى.
- الوصول إلى طلب غير مسند إليه.
- تغيير organization_id.
- فتح ملفات مستخدم آخر.
- تعديل حالة الطلب بصورة غير مسموحة.

## مستخدم إداري سيئ الاستخدام

قد يحاول:

- تصدير بيانات كثيرة.
- تعطيل مستخدمين.
- تغيير أدوار.
- قراءة بيانات دون حاجة.
- حذف أو إخفاء سجلات.

## تسريب تقني

قد يحدث بسبب:

- رفع ملف .env إلى GitHub.
- وضع Service Role Key في React.
- جعل Storage Bucket عامًا.
- كتابة سياسات RLS ضعيفة.
- ظهور Stack Trace للمستخدم.
- استخدام رابط ملف دائم.
- تثبيت مكتبة غير آمنة.
- خطأ في إعداد DNS أو النشر.

# 7. مبدأ أقل صلاحية

يجب منح كل مستخدم أقل قدر ممكن من الصلاحيات.

## مدير الشركة

يصل إلى بيانات شركته فقط.

## المشرف

يصل إلى المواقع المسموح له بها.

## الفني

يصل إلى الطلبات المسندة إليه فقط.

## المبلّغ

يصل إلى نموذج الإبلاغ وطلبه فقط.

## مدير المنصة

ينفذ عمليات الإدارة من خلال وظائف خادم آمنة، وليس من خلال صلاحيات واسعة داخل الواجهة.

# 8. الفصل بين الشركات Multi-Tenancy

FixFlow يدعم عدة شركات داخل النظام نفسه.

يجب أن يكون لكل سجل تشغيلي:

- organization_id

يشمل ذلك:

- profiles
- locations
- categories
- assets
- tickets
- ticket_comments
- ticket_attachments
- ticket_history
- notifications
- audit_logs
- subscriptions
- settings

## القاعدة

يجب أن يساوي organization_id في السجل organization_id الخاص بالمستخدم.

## ممنوع

- الاعتماد على organization_id المرسل من الواجهة.
- السماح للمستخدم بتغييره.
- جلب الطلب باستخدام id فقط.
- استخدام استعلامات لا تتحقق من الشركة.
- إنشاء ملف داخل مجلد شركة أخرى.

# 9. المصادقة Authentication

يستخدم النظام:

- Supabase Auth.

## الوظائف المطلوبة

- تسجيل الدخول.
- تسجيل الخروج.
- استرجاع كلمة المرور.
- تغيير كلمة المرور.
- إرسال دعوة.
- انتهاء الجلسة.
- تعطيل الحساب.
- إنهاء الجلسات عند الحاجة.

## قواعد تسجيل الدخول

1. استخدام HTTPS.
2. عدم تخزين كلمة المرور في Local Storage.
3. الاعتماد على إدارة الجلسات الرسمية.
4. التحقق من is_active بعد الدخول.
5. التحقق من حالة الشركة.
6. التحقق من الاشتراك.
7. عدم كشف هل البريد موجود في استرجاع كلمة المرور.
8. منع المحاولات المتكررة.
9. تسجيل المحاولات المشبوهة.
10. إظهار رسالة عامة عند الخطأ.

## رسالة خطأ مناسبة

البريد الإلكتروني أو كلمة المرور غير صحيحة.

## رسالة غير مناسبة

هذا البريد موجود ولكن كلمة المرور غير صحيحة.

الرسالة الثانية تكشف وجود الحساب.

# 10. سياسة كلمات المرور

يجب فرض سياسة مناسبة تشمل:

- حد أدنى لا يقل عن 8 أحرف.
- تشجيع استخدام 12 حرفًا أو أكثر.
- منع كلمات المرور الشائعة.
- دعم الأحرف والأرقام والرموز.
- عدم عرض كلمة المرور.
- السماح بإظهارها مؤقتًا بزر واضح.
- عدم إرسال كلمة المرور بالبريد.
- عدم إنشاء كلمة مرور ثابتة لجميع المستخدمين.
- عدم تسجيل كلمة المرور في السجلات.

## تغيير كلمة المرور

يطلب من المستخدم:

- كلمة المرور الجديدة.
- تأكيد كلمة المرور.
- تسجيل الخروج من الجلسات الأخرى عند الحاجة.

# 12. إدارة الجلسات

يجب:

- التحقق من الجلسة عند فتح الصفحات الخاصة.
- إنهاء الجلسة عند تسجيل الخروج.
- منع الحساب المعطل من استخدام جلسة قديمة.
- التحقق من انتهاء الرمز.
- إعادة التوجيه إلى تسجيل الدخول عند انتهاء الجلسة.
- عدم وضع رمز الجلسة داخل رابط URL.
- عدم إرسال الرموز عبر البريد أو الرسائل.

## عند تعطيل مستخدم

1. تحديث is_active إلى false.
2. منع العمليات الجديدة.
3. إنهاء الجلسات عند الإمكان.
4. الاحتفاظ بسجلات نشاطه السابقة.

# 13. التفويض Authorization

بعد معرفة هوية المستخدم، يجب التحقق مما يستطيع فعله.

يجب التحقق من:

- الدور.
- الشركة.
- الموقع.
- حالة الحساب.
- حالة الشركة.
- حالة الاشتراك.
- ملكية السجل.
- حالة الطلب.
- نوع العملية.

## مثال

قبل تعيين فني:

1. المستخدم مسجل.
2. المستخدم COMPANY_ADMIN أو SUPERVISOR.
3. الطلب يتبع شركته.
4. الموقع مسموح له.
5. الفني يتبع الشركة.
6. الفني مرتبط بالموقع.
7. الفني نشط.
8. الطلب في حالة تسمح بالتعيين.

# 14. حماية المسارات في React

يجب إنشاء:

- ProtectedRoute.
- RoleRoute.
- SubscriptionRoute.
- OrganizationGuard.

## ProtectedRoute

يتحقق من وجود جلسة.

## RoleRoute

يتحقق من الدور.

## SubscriptionRoute

يتحقق من أن الشركة نشطة.

## عند الفشل

- عدم وجود جلسة: الانتقال إلى /login.
- عدم وجود صلاحية: عرض 403.
- انتهاء الاشتراك: عرض صفحة الاشتراك.
- الحساب المعطل: تسجيل الخروج وعرض رسالة.

## ملاحظة

حماية React لا تكفي وحدها؛ لأنها حماية للواجهة فقط.

يجب أن تدعمها:

- RLS.
- Edge Functions.
- التحقق من الخادم.

## DELETE

# 17. سياسات profiles

## SELECT

- المستخدم يرى ملفه.
- مدير الشركة يرى مستخدمي شركته.
- المشرف يرى بيانات المستخدمين الضرورية في مواقعه.
- الفني يرى بياناته وبيانات محدودة مرتبطة بطلبه.

## UPDATE

المستخدم يستطيع تعديل:

- full_name.
- phone.
- avatar_url.
- notification preferences.

المستخدم لا يستطيع تعديل:

- role.
- organization_id.
- is_active.
- id.
- created_at.

## INSERT

يتم عبر وظيفة دعوة آمنة.

## DELETE

يفضل منعه واستخدام التعطيل.

# 20. سياسات tickets

## SELECT

- مدير الشركة: جميع طلبات الشركة.
- المشرف: طلبات المواقع المسموح بها.
- الفني: الطلبات المسندة إليه.
- المبلّغ: من خلال public_tracking_token ووظيفة آمنة.

## INSERT

- مدير الشركة.
- المشرف.
- الصفحة العامة من خلال create-ticket Edge Function.

## UPDATE

يفضل عدم السماح بتحديث جميع الحقول مباشرة.

تستخدم وظائف مخصصة مثل:

- assign-technician.
- change-ticket-status.
- close-ticket.
- reopen-ticket.

## DELETE

ممنوع تمامًا.

# 28. حماية QR

- طويلًا.
- فريدًا.
- غير متسلسل.
- غير مبني على asset_id فقط.
- غير قابل للتخمين بسهولة.

## ممنوع وضع البيانات التالية داخل QR

- مفتاح API.
- organization_id بصورة مكشوفة دون حاجة.
- بريد المدير.
- بيانات تسجيل دخول.
- روابط ملفات خاصة.
- بيانات الجهاز الحساسة.
- رقم تسلسلي سري إذا لم تكن هناك حاجة.

## عند تسريب QR

يستطيع المدير:

1. تعطيل الرمز.
2. إنشاء رمز جديد.
3. إبطال القديم.
4. تسجيل العملية.

# 29. حماية public_tracking_token

- عشوائيًا.
- طويلًا.

- غير ظاهر في التقارير الداخلية غير الضرورية.

- بيانات المشرف الكاملة.
- بيانات الفني الخاصة.
- تكلفة القطع.
- سجل التدقيق.
- معرفات قاعدة البيانات.
- بيانات شركة أخرى.

# 30. Rate Limiting

يجب منع الطلبات المتكررة بصورة كبيرة.

## الصفحات المستهدفة

- تسجيل الدخول.
- نسيت كلمة المرور.
- إنشاء طلب QR.
- متابعة الطلب.
- إعادة فتح الطلب.
- إرسال تقييم.
- رفع الملفات.
- Edge Functions العامة.

## أمثلة حدود مبدئية

### تسجيل الدخول

عدد محدود من المحاولات لكل IP أو حساب خلال فترة.

### إنشاء طلب QR

عدد محدود من الطلبات لكل IP وqr_token.

### متابعة الطلب

عدد محدود من الاستعلامات لكل tracking token وIP.

### رفع الملفات

عدد وحجم محدود لكل طلب.

## عند تجاوز الحد

- إرجاع HTTP 429.
- عرض رسالة:
  تم إرسال عدد كبير من الطلبات. حاول لاحقًا.
- تسجيل الحدث.
- عدم كشف معلومات داخلية.

# 33. الحماية من SQL Injection

## يجب

- استخدام Supabase Client.
- استخدام Parameters.
- استخدام RPC معرفة مسبقًا.
- عدم بناء SQL من نص المستخدم.
- عدم دمج القيم داخل query string يدويًا.

## ممنوع

إنشاء استعلام SQL باستخدام:

- string concatenation.
- template strings مع مدخل المستخدم.
- تنفيذ SQL خام قادم من المتصفح.
