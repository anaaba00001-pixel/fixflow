# FixFlow — خطة الاختبار وحالات الاختبار

## 1. هدف هذا الملف

يحدد هذا الملف جميع الاختبارات المطلوبة للتأكد من أن نظام FixFlow:

- يعمل حسب المتطلبات.
- يحافظ على عزل بيانات الشركات.
- يطبق الأدوار والصلاحيات.
- يمنع الانتقالات الخاطئة لحالات الطلب.
- يعمل على الكمبيوتر والجوال.
- يحمي الملفات والمرفقات.
- يرسل الإشعارات بصورة صحيحة.
- ينتج تقارير دقيقة.
- يتعامل مع الأخطاء دون فقد البيانات.
- يكون جاهزًا للنشر والاستخدام الحقيقي.

يستخدم هذا الملف أثناء:

- تطوير كل وظيفة.
- مراجعة الكود.
- اختبار قاعدة البيانات.
- اختبار RLS.
- اختبار Edge Functions.
- اختبار واجهات React.
- اختبار النسخة التجريبية.
- اختبار ما قبل النشر.
- اختبار قبول المستخدم.

# 3. أنواع الاختبارات

يجب إجراء الأنواع التالية:

## 3.1 اختبار الوحدات Unit Testing

يختبر الدوال الصغيرة منفصلة.

أمثلة:

- توليد رقم الطلب.
- حساب موعد الاستحقاق.
- تحويل اسم الحالة.
- حساب مدة الإصلاح.
- التحقق من نوع الملف.
- التحقق من انتقال الحالة.

## 3.2 اختبار التكامل Integration Testing

يختبر عمل أكثر من جزء معًا.

أمثلة:

- إنشاء طلب مع حفظ المرفق.
- تعيين فني مع إنشاء إشعار.
- إغلاق الطلب مع تحديث الجهاز.
- إنشاء مستخدم مع إرسال دعوة.

## 3.3 اختبار الواجهة UI Testing

يختبر:

- ظهور العناصر.
- النماذج.
- الأزرار.
- الفلاتر.
- الرسائل.
- الجداول.
- توافق RTL.

## 3.4 اختبار النظام End-to-End

يختبر رحلة كاملة.

مثال:

QR → طلب جديد → تعيين فني → إصلاح → اعتماد → إغلاق.

## 3.5 اختبار الأمان Security Testing

يختبر:

- عزل الشركات.
- الصلاحيات.
- RLS.
- الملفات.
- QR.
- الرموز العامة.
- رفع الأدوار.
- XSS.
- Rate Limiting.

## 3.6 اختبار الأداء Performance Testing

يختبر:

- سرعة الصفحات.
- القوائم الكبيرة.
- البحث.
- التقارير.
- رفع الملفات.
- العمليات المتزامنة.

## 3.7 اختبار قبول المستخدم UAT

ينفذه مستخدم فعلي أو جهة تجريبية للتأكد من سهولة النظام.

## 3.8 اختبار الانحدار Regression Testing

يعاد بعد كل تعديل للتأكد من أن الوظائف القديمة ما زالت تعمل.

# 4. بيئات الاختبار

## Development

تستخدم أثناء التطوير المحلي.

لا تحتوي على بيانات حقيقية.

## Staging

تستخدم للاختبار قبل الإنتاج.

يجب أن تكون منفصلة عن Production.

## Production

لا تستخدم للاختبار العشوائي.

تستخدم فقط اختبارات تحقق بسيطة بعد النشر.

# 7. مستويات أولوية الاختبار

## P0 — حرج

فشل الاختبار يمنع النشر.

أمثلة:

- تسريب بيانات شركة.
- فشل تسجيل الدخول.
- إمكانية رفع الدور.
- فقد طلب صيانة.
- كشف Service Role Key.

## P1 — عالٍ

يجب إصلاحه قبل الإنتاج.

أمثلة:

- فشل تعيين الفني.
- فشل إغلاق الطلب.
- عدم وصول إشعار مهم.
- خطأ في صلاحيات المشرف.

## P2 — متوسط

يمكن إصلاحه قبل الإطلاق أو بعده بوقت قصير.

أمثلة:

- مشكلة ترتيب جدول.
- خطأ بسيط في تقرير.
- رسالة غير واضحة.

## P3 — منخفض

تحسين غير مانع للنشر.

أمثلة:

- اختلاف بسيط في المسافات.
- تحسين لون أو أيقونة.

# 12. اختبارات تسجيل الدخول والمصادقة

## AUTH-001 — تسجيل دخول صحيح

الأولوية: P0

الشروط:

- حساب نشط.
- شركة نشطة.
- اشتراك صالح.

الخطوات:

1. فتح صفحة تسجيل الدخول.
2. إدخال بريد صحيح.
3. إدخال كلمة مرور صحيحة.
4. الضغط على تسجيل الدخول.

النتيجة المتوقعة:

- نجاح تسجيل الدخول.
- حفظ الجلسة.
- توجيه المستخدم إلى الصفحة المناسبة لدوره.
- تحديث last_login_at.
